## JS functions and parameters

A **function** is a reusable piece of code with a name. You define it once and call it as many times as you like, optionally passing in different inputs. Functions are the most powerful tool in the language — they're how you avoid repeating yourself, how you compose complex behavior from simple parts, and how every higher-level pattern you'll meet (events, promises, React components, server handlers) ultimately works under the hood.

<Analogy>
A function is **a recipe you write down once and run many times**.

Imagine you make pancakes most Sundays. You could re-derive the recipe every time — "what was the ratio of flour to milk? how hot is medium-high again?" — but instead you wrote it down. Now whenever you want pancakes you grab the card, follow the steps, and you're eating in 15 minutes. The recipe is the function. Each Sunday is a *call* to the function — same recipe, different mornings.

Recipes take *ingredients* — the inputs that vary each time. The pancake recipe takes "how many servings" as an input; you scale up for guests. Functions take **parameters** for the same reason: the body of the recipe stays the same, but the specific inputs change at call time.

A recipe also produces an *output* — the dish. A function can `return` a value the caller uses (the pancakes you take to the table). Or it might just *do* something (clean up the kitchen) without returning anything useful — what we call a "side effect."

The cooking analogy holds for almost every function decision: keep recipes short (small functions read better than monster ones). Give them clear names ("make_pancakes," not "do_stuff"). Have them either return a value OR have side effects, not both, where possible.
</Analogy>

### Three ways to write a function

JavaScript gives you three syntaxes. They look different but do the same job.

#### 1. Function declaration

```js
function greet(name) {
  return `Hello, ${name}!`;
}

greet("Aisha");   // → "Hello, Aisha!"
```

The classic form. Two unique properties: the function is **hoisted** (you can call it before it appears in the source) and it has its own `this` binding (which matters for older OOP-style code).

#### 2. Function expression — assigning a function to a variable

```js
const greet = function(name) {
  return `Hello, ${name}!`;
};

greet("Aisha");
```

The function is a *value* assigned to a variable. NOT hoisted — must be defined before use. Pretty much obsolete now that arrow functions exist.

#### 3. Arrow function — the modern default

```js
const greet = (name) => `Hello, ${name}!`;
```

Three things about arrows:

- **No `function` keyword.** Just `(parameters) => body`.
- **Implicit return.** If the body is a single expression, it returns that expression — no `return` keyword needed.
- **No own `this`.** They inherit `this` from the surrounding scope. Almost always what you want.

For a multi-line body, use braces and write `return` explicitly:

```js
const greet = (name) => {
  const upper = name.toUpperCase();
  return `Hello, ${upper}!`;
};
```

**Use arrow functions by default.** Use a regular `function` declaration when you specifically need its `this` behavior (rare in modern code) or when hoisting matters.

### Parameters and arguments

The names in the definition are **parameters**; the values you pass in at the call site are **arguments**:

```js
function add(a, b) {       // a, b are parameters
  return a + b;
}

add(2, 3);                 // 2, 3 are arguments
```

#### Default parameters

```js
function greet(name = "Guest") {
  return `Hello, ${name}!`;
}

greet();           // "Hello, Guest!"
greet("Aisha");    // "Hello, Aisha!"
```

The `= "Guest"` is used when the caller doesn't pass that argument (or passes `undefined`). Cleaner than the older `name = name || "Guest"` pattern.

#### Rest parameters

To accept *any number* of arguments:

```js
function sum(...numbers) {
  return numbers.reduce((acc, n) => acc + n, 0);
}

sum(1, 2);            // 3
sum(1, 2, 3, 4, 5);   // 15
```

The `...` ("rest") collects all remaining arguments into an array. Must be the last parameter.

#### Object destructuring in parameters

For functions with many configuration options, an object parameter is much nicer than a long positional list:

```js
// HARDER TO READ — what does each number mean?
makeButton("Save", true, "primary", "md", false);

// MUCH BETTER
function makeButton({ label, primary = false, size = "md", disabled = false }) {
  // ...
}

makeButton({ label: "Save", primary: true });
```

The caller passes named options; missing keys get defaults. This is the standard pattern in modern JS APIs — React props, library configs, function options.

### Return values

`return` exits the function and hands back a value:

```js
function isAdult(age) {
  return age >= 18;
}

const ok = isAdult(22);   // ok = true
```

A function with no `return` (or `return` with no value) returns `undefined`:

```js
function logIt(x) {
  console.log(x);
  // no return
}

const r = logIt("hi");   // r is undefined
```

You can have multiple `return`s in a function — guard clauses use this:

```js
function describe(n) {
  if (n === 0) return "zero";
  if (n < 0)   return "negative";
  if (n > 100) return "huge";
  return "small positive";
}
```

### Functions as values (first-class functions)

JavaScript treats functions as values. You can:

- Assign a function to a variable.
- Pass a function as an argument to another function.
- Return a function from a function.
- Store functions in arrays or objects.

This is what makes things like `arr.map(fn)`, event listeners, promises, and React all work:

```js
// pass a function as an argument
[1, 2, 3].map((n) => n * 2);

// store functions in an object — looks like a router
const handlers = {
  click: () => alert("clicked"),
  hover: () => console.log("hovered"),
};

handlers.click();
```

Functions being first-class is the property the next 20 lessons leans on. The mental model: **functions are values you can store, pass, and call**.

### Side effects vs pure functions

A **pure** function: same inputs always produce the same output, and it doesn't change anything outside itself.

```js
// Pure — depends only on inputs, returns a value
function add(a, b) {
  return a + b;
}
```

A function with **side effects**: it touches something outside itself (the DOM, a global variable, network, console).

```js
let count = 0;
// Side effect — mutates count, doesn't return anything useful
function bump() {
  count++;
}
```

Both are legitimate. The rule of thumb that pays off massively: **prefer pure functions where you can, isolate side effects where you can't**. Pure functions are testable, reusable, and don't surprise you. Side effects are necessary at the *edges* of your program — the DOM, the database, the network. Keep them out of the middle.

<InterviewQuestion difficulty="Beginner">

**Q:** What's the difference between a function declaration and an arrow function?

**A:** Three concrete differences:

1. **Syntax.** Declaration uses `function`; arrow uses `=>`.
2. **Hoisting.** Function declarations are hoisted — you can call them before their definition line. Arrow functions (assigned to `const`/`let`) are not.
3. **`this` binding.** Function declarations have their own `this` (determined by *how* they're called). Arrow functions **inherit `this`** from the surrounding scope and have no `this` of their own.

```js
greet();                           // works — hoisted
function greet() { return "hi"; }

byeArrow();                        // ReferenceError — not hoisted
const byeArrow = () => "bye";
```

The `this` difference is the big one for modern code. Arrow functions don't change `this` inside them, which is what you want 99% of the time (e.g. inside event handlers and callbacks). The `function` keyword's `this` magic is mostly a footgun outside of class methods and constructor functions.

Modern advice: use arrows by default; reach for `function` when you genuinely need a different `this` (rare) or hoisting (also rare).

</InterviewQuestion>

<InterviewQuestion difficulty="Beginner">

**Q:** What's the difference between parameters and arguments?

**A:**

- **Parameters** are the names in the function's *definition*. They're placeholders.
- **Arguments** are the actual *values* passed in at the call site.

```js
function greet(name, age) {     // name, age are parameters
  return `${name} is ${age}`;
}

greet("Aisha", 22);             // "Aisha", 22 are arguments
```

People use the words interchangeably and most of the time it doesn't matter. The distinction comes up in two contexts:

- **Default parameters**: `function greet(name = "Guest") { … }` — `"Guest"` is the **default parameter value**, used when no argument is passed.
- **Rest parameters**: `function sum(...nums) { … }` — `...nums` is a **rest parameter** that collects multiple arguments into an array.

</InterviewQuestion>

<InterviewQuestion difficulty="Intermediate">

**Q:** What does it mean that "functions are first-class" in JavaScript?

**A:** "First-class" means functions are treated as **values, like numbers and strings** — you can store them in variables, pass them as arguments, return them from other functions, and put them in arrays and objects.

```js
// Assign to a variable
const greet = () => "hi";

// Pass as an argument
[1, 2, 3].map((n) => n * 2);

// Return from a function
function multiplier(factor) {
  return (n) => n * factor;
}
const double = multiplier(2);   // double is a function
double(5);                      // → 10

// Store in an object
const handlers = { click: () => …, hover: () => … };
```

This single property is what makes **higher-order functions** possible (`map`, `filter`, `reduce`), what powers **callbacks** (event listeners, `setTimeout`), how **promises** work (`.then(fn)`), and how React components compose (a component is a function that returns markup; you pass functions as props).

Most languages have first-class functions now, but JavaScript was one of the early popular languages where this was natural. It's the property that makes 90% of modern JS patterns possible.

</InterviewQuestion>

<InterviewQuestion difficulty="Intermediate">

**Q:** What does it mean to "prefer pure functions," and why do people care?

**A:** A **pure function** has two properties:

1. **Deterministic** — same inputs always produce the same output. No randomness, no clock, no global state.
2. **No side effects** — doesn't modify anything outside itself: no mutating arguments, no writing to the DOM, no logging, no fetching.

```js
// Pure
function add(a, b) { return a + b; }

// Impure (mutates input)
function addId(user) { user.id = Math.random(); return user; }

// Impure (depends on external state)
function timestamp() { return Date.now(); }
```

Why prefer them:

1. **Easy to test.** No setup or mocks; pass inputs, check outputs.
2. **Easy to reason about.** Reading the function tells you everything it does.
3. **Composable.** Two pure functions chain cleanly because neither one cares about external state.
4. **Cacheable.** Same inputs → same output → safe to memoize.
5. **Concurrency-friendly.** No shared mutable state to fight over.

The rule isn't "all functions must be pure" — that's impossible in any real program (eventually you have to write to the screen, fetch data, log errors). The rule is "**push side effects to the edges**." The middle of your program — the logic, the calculations, the transformations — should be pure. The boundary functions that touch the DOM, the network, the database can be impure but are clearly labeled and isolated. React, Redux, functional libraries, and most modern architectures lean heavily on this idea.

</InterviewQuestion>
