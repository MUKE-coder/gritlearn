## Milestone — your first standalone Express API

You've built every piece of this in isolation across Phase 4: Express routes, request/response, middleware, REST endpoints, Prisma + Postgres, env config, JWT sessions, authorization, input validation, CORS, frontend ↔ backend wiring. This lesson is the milestone — you'll wire them all together into one runnable API, end to end, and ship it.

Treat this lesson differently from the others. There's no new concept. There's a **specification, a directory layout, and a checklist**. Build the API yourself, in your terminal, from scratch. When you finish, you'll have shipped the same shape of API that powers half the SaaS products you use every day.

<Analogy>
Every lesson in this phase has been **one chapter of a manual** — how the carburettor works, how the spark plugs fire, how the timing belt syncs the camshaft to the crankshaft. Each chapter taught you a piece in isolation: the same piece, removed from the engine, on a clean workbench, with a labelled diagram.

The milestone is **the empty garage and a parts pile.** You walk in. The carburettor, the spark plugs, the timing belt, the camshaft are all on the floor. There's a chassis with no engine in it. The spec is taped to the wall. Your job is to assemble a working engine.

Two things change when the pieces have to fit together:

1. **The seams between parts matter more than the parts themselves.** Each part is well-understood. What makes a working engine is the *order* you bolt them in, the *bolts* that connect them, the *gaskets* that seal the joints. In code: each middleware works fine in isolation; what's hard is wiring middleware A's output to middleware B's expected input, in the right order, with the right shapes.

2. **You can't read your way through the build.** Every chapter so far had a Read → Run → Move-on flow. The milestone is Read → Plan → Build → Debug → Repeat. The lesson is the act of building.

Most students discover something in the milestone they thought they understood from a lesson but didn't. That's not a failure — that's how skills bake in. The friction is the point.
</Analogy>

### The API spec — a blog backend

You're building the backend for a multi-user blog. Functional requirements:

- **Users** can register with email + password, log in, and stay logged in via JWT.
- **Posts** belong to a user. A user can create, list, read, update, and delete their own posts.
- **Public read access** to all published posts at `GET /posts`. (Drafts stay private.)
- **Single-post page** at `GET /posts/:id` — public if the post is published, owner-only otherwise.
- **Profile editing** at `PATCH /users/me` — name, bio, avatar URL.
- **Rate limiting** on auth routes: 5 attempts per 10 minutes per IP for `/auth/login` and `/auth/register`.

Out of scope (deliberately): comments, likes, image uploads, search. You'll add those in your portfolio version.

### The route table

```
Method  Path                  Auth         Description
─────── ───────────────────── ──────────── ───────────────────────────
POST    /auth/register        Public       Create a new user account
POST    /auth/login           Public       Exchange password for JWT
GET     /auth/me              Required     Current user from token

GET     /posts                Public       List published posts (paginated)
POST    /posts                Required     Create a post (owner = current user)
GET     /posts/:id            Mixed        Public if published, owner if draft
PATCH   /posts/:id            Owner-only   Update title / body / published
DELETE  /posts/:id            Owner-only   Delete the post

GET     /users/:id            Public       Public profile (name, bio)
PATCH   /users/me             Required     Update own profile
```

Three auth flavours show up — Public, Required, Owner-only — and the routing has to enforce each. That's the authorization concept doing real work for you.

### The middleware stack — order matters

In `src/server.js` the middleware lines up in this order:

```js
import express from "express";
import cors from "cors";
import helmet from "helmet";
import morgan from "morgan";
import { env } from "./env.js";

const app = express();

// 1. Security baseline — sets a stack of safe HTTP headers.
app.use(helmet());

// 2. CORS — must run before route handlers so the preflight gets answered.
app.use(cors({
  origin: env.FRONTEND_URL.split(","),
  credentials: true,
}));

// 3. Body parsing — JSON only.
app.use(express.json({ limit: "1mb" }));

// 4. Request logging — pretty in dev, structured in prod.
app.use(morgan(env.NODE_ENV === "production" ? "combined" : "dev"));

// 5. Routes — auth first (it sets up req.user for subsequent ones).
app.use("/auth",  authRouter);
app.use("/posts", postsRouter);
app.use("/users", usersRouter);

// 6. 404 fallback — any path that didn't match.
app.use((req, res) => res.status(404).json({ error: "Not Found" }));

// 7. Error handler — last, ALWAYS. Catches errors from route handlers
//    (which call next(err) or just throw inside an async handler if
//    you wrap them with express-async-errors).
app.use((err, req, res, next) => {
  console.error(err);
  res.status(err.status ?? 500).json({
    error: err.message ?? "Internal Server Error",
  });
});

app.listen(env.PORT, () => {
  console.log(`API listening on http://localhost:${env.PORT}`);
});
```

Three mistakes new builders make with middleware order:

1. **Mounting CORS after routes.** Result: preflight requests hit the 404 handler instead of the CORS middleware. Browser blocks every cross-origin call.
2. **Mounting the error handler before routes.** Express only treats a four-arg middleware as an error handler if it's *after* the routes. Put it first and it's just a normal middleware that never fires.
3. **No body parser, expecting `req.body` to be populated.** `req.body` is `undefined` until `express.json()` (or `urlencoded()`) runs. New devs spend an embarrassing amount of time on this one.

### The Prisma schema

`prisma/schema.prisma`:

```prisma
generator client {
  provider = "prisma-client-js"
}

datasource db {
  provider = "postgresql"
  url      = env("DATABASE_URL")
}

model User {
  id        String   @id @default(cuid())
  email     String   @unique
  password  String                       // bcrypt hash
  name      String
  bio       String?
  avatarUrl String?
  posts     Post[]
  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt
}

model Post {
  id        String   @id @default(cuid())
  title     String
  body      String
  published Boolean  @default(false)
  authorId  String
  author    User     @relation(fields: [authorId], references: [id], onDelete: Cascade)
  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt

  @@index([authorId, published])
}
```

`onDelete: Cascade` is doing real work — deleting a user cleans up their posts in one transaction. Without it you'd hit a foreign key error.

### The checklist

Don't read the spec and start coding. Work the checklist. Each item is something you'd skip and regret in a real project.

**Setup (≈ 30 min)**
- [ ] `pnpm init`, install: `express`, `prisma`, `@prisma/client`, `bcrypt`, `jsonwebtoken`, `zod`, `cors`, `helmet`, `morgan`, `express-rate-limit`, `dotenv`.
- [ ] Dev deps: `prisma`, `nodemon`.
- [ ] `.env.example` with every env var (no secrets). `.env` (gitignored) with real values.
- [ ] `pnpm prisma migrate dev --name init` after writing the schema.

**Middleware (≈ 1 hour)**
- [ ] `requireAuth`: extracts `Bearer` token, verifies with `JWT_SECRET`, attaches `req.user`. Returns `401` cleanly on missing/invalid tokens.
- [ ] `requireOwner(resource)`: takes a string param name (`":id"`), looks up the resource, compares `resource.authorId === req.user.id`. `404` if not found, `403` if not owner.
- [ ] `validate(schema)`: wraps a zod schema, parses `req.body`, returns `422` with the issues on failure.
- [ ] Rate limit middleware on `/auth/*` routes.

**Routes (≈ 2 hours)**
- [ ] Implement all ten routes from the spec table.
- [ ] Confirm the auth flavour on each (Public / Required / Owner-only).
- [ ] Use `validate(…)` on every `POST` and `PATCH`.
- [ ] Pagination on `GET /posts`: query params `?page=1&limit=20`, default 20, max 100.

**Manual test (≈ 30 min)**
- [ ] Register a user via `curl` or Postman. Verify the password is *not* returned in the response.
- [ ] Log in. Save the token.
- [ ] Create a post with the token. Verify `authorId = your-user-id` server-side.
- [ ] List `GET /posts` without a token — should return only published posts.
- [ ] Try to update a *different* user's post — must get `403`.
- [ ] Hit `/auth/login` six times wrong — sixth attempt must get `429`.

**Polish (≈ 30 min)**
- [ ] README with: prerequisites, install steps, env vars, `pnpm dev`, route table.
- [ ] `package.json` scripts: `dev`, `start`, `db:generate`, `db:migrate`, `db:studio`.
- [ ] Commit history that tells the story of how you built it.

### The bar to clear

When all the checkboxes are ticked, you've shipped a backend that, technically speaking, looks like the early-day Stripe / Notion / Linear backends. A small team could grow the same skeleton to power a real product.

That's the goal of Phase 4 in one sentence: **you can now write the half of the system that lives behind the API**.
