Merge vs. rebase — same situation, two histories

Setup: You branched off main at B, did commits C and D on your feature branch. While you were busy, a teammate pushed X and Y to main. Now you need to integrate. Two ways.

git merge feature → main

M is a new "merge commit" with TWO parents (Y and D). Both timelines are preserved in history.

Pros: Preserves literal history. Safe on shared branches. The merge commit documents "I integrated branch X here."
Cons: `git log` reads as a non-linear graph. Lots of merge commits can clutter history.

git rebase main, then fast-forward

Your commits C and D are replayed on top of Y as new commits C' and D'. Linear history; no merge commit.

Pros: `git log` reads as a clean sequence. No "merge noise." Easier to follow what happened.
Cons: Rewrites your branch's commits (new SHAs). Never do this on a branch others have pulled. Force-push needed.

The everyday rule

Rebase your private feature branch onto main to tidy it up before merging. Then merge (not rebase) into main. Some teams prefer always-merge for a literal history; others prefer rebase-then-merge for a cleaner one. Match your team's convention — consistency matters more than the choice.
