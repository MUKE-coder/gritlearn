The await-fetch pattern, end to end

A real "page fetches data, renders, handles errors and loading" walkthrough.

1 The page — async server component

app/products/page.tsx
import { Suspense } from "react";
import { ProductGrid } from "@/components/ProductGrid";
import { RecentReviews } from "@/components/RecentReviews";

export default async function ProductsPage() {
  // Parallel fetches — both start at the same time
  const [products, featured] = await Promise.all([
    fetch("https://api.example.com/products").then(r => r.json()),
    fetch("https://api.example.com/featured").then(r => r.json()),
  ]);

  return (
    <main className="p-8">
      <h1>Products</h1>
      <ProductGrid products={products} featured={featured} />

      <Suspense fallback={<p>Loading recent reviews…</p>}>
        <RecentReviews /> {/* a slower component, streams in */}
      </Suspense>
    </main>
  );
}
The page itself awaits its primary data — no useEffect, no loading state for the products. The RecentReviews component (which fetches its own data) is wrapped in Suspense so it can stream in later without blocking the page.

2 The slow child — its own server component

components/RecentReviews.tsx
// also a server component (no "use client")
export async function RecentReviews() {
  const reviews = await fetch("https://api.example.com/reviews", {
    next: { revalidate: 60 } // ISR — cache for 60s
  }).then(r => r.json());

  return (
    <section>
      <h2>Recent reviews</h2>
      <ul>
        {reviews.map((r: Review) => (
          <li key={r.id}>{r.body}</li>
        ))}
      </ul>
    </section>
  );
}
Each fetch can have its own cache strategy. Products is full-fresh; reviews are ISR with 60s revalidation.

3 The loading shell

app/products/loading.tsx
export default function Loading() {
  return (
    <main className="p-8">
      <div className="animate-pulse h-8 w-32 bg-gray-200 rounded" />
      <div className="mt-4 grid grid-cols-3 gap-4">
        {[1,2,3,4,5,6].map(i => (
          <div key={i} className="h-40 bg-gray-200 rounded animate-pulse" />
        ))}
      </div>
    </main>
  );
}
Shown automatically while page.tsx is rendering. Implicit Suspense boundary around the whole route.

4 The error boundary

app/products/error.tsx
"use client"; // error.tsx must be a client component

export default function Error({
  error,
  reset,
}: { error: Error; reset: () => void }) {
  return (
    <main className="p-8 text-red-700">
      <h1>Couldn't load products</h1>
      <p>{error.message}</p>
      <button
        onClick={reset}
        className="mt-4 rounded bg-red-100 px-4 py-2"
      >
        Try again
      </button>
    </main>
  );
}
If page.tsx (or any server component in the route) throws, this is rendered in its place. The layout around it still shows.

What you don't see in the user's network panel

  • No XHR / fetch calls to a separate API for the products data — it was server-fetched.
  • The HTML response contains the products data already rendered.
  • The "Loading recent reviews…" fallback streams in first; the real content replaces it within the same response.
  • If the products fetch fails, the error UI ships instead of broken HTML.
