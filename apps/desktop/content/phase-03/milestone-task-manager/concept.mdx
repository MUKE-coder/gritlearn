## Milestone — full-stack task manager

You've now learned every piece of a modern Next.js full-stack app:

- The App Router, layouts, navigation, server vs client components.
- Rendering strategies and data fetching.
- Route handlers and server actions for mutations.
- Postgres as the storage layer, Prisma as the typed API.
- Auth.js for sign-in, middleware + page-level checks for protection.
- Environment variables, secrets, deployment to Vercel.

The milestone is to put all of it into one app — a multi-user task manager — and ship it to a real URL. By the end you'll have a working `https://your-tasks.vercel.app` (or your own custom domain) that:

- Lets anyone sign in with GitHub.
- Stores their tasks in a real Postgres database.
- Shows the right user's tasks (never anybody else's).
- Updates fluidly without page reloads, using server actions and revalidation.
- Survives reload, restart, and time zones intact.

You will ship this. You'll feel the moment when you click "Add task" on production and your sister opens the URL on her phone and sees an empty list — because you correctly scoped tasks to each user.

### What you'll build

**Multi-user task manager.** Each signed-in user has their own tasks. The UI is intentionally minimal — single page, header, "add task" form, list of tasks with done/delete actions. The point is the *architecture*, not the design polish.

Feature checklist:

- [ ] GitHub sign-in. Anyone with a GitHub account can register / log in.
- [ ] Each user sees only their own tasks.
- [ ] Add a task (title required, optional due date).
- [ ] Toggle a task as done / not done.
- [ ] Delete a task (with a confirmation — or skip and use soft-delete if you want a stretch goal).
- [ ] Filter: all / open / done.
- [ ] No page reloads — every action uses a server action with `revalidatePath`.
- [ ] Loading state visible while server actions run (`useFormStatus`).
- [ ] Inline validation errors.
- [ ] 404 page when an unauthenticated user hits `/dashboard`.
- [ ] Deployed to Vercel with a real Postgres database.

Optional stretch goals:

- Tags / categories for each task.
- Drag-to-reorder (client state + server-action persist on drop).
- Per-user themes (dark / light toggle persisted in DB).
- Public sharing — generate a read-only URL anyone can view.
- Webhook on task completion (Slack ping when "review PR" gets ticked).

### The build, in phases

The phased plan below is how I'd ship it — your branches and PR shape can vary. Each phase ends with a working, committable state.

#### Phase A — scaffold + auth (Day 1)

```bash
npx create-next-app@latest my-tasks --typescript --tailwind --app
cd my-tasks
npm i prisma @prisma/client @auth/prisma-adapter next-auth@beta zod bcrypt
npm i -D @types/bcrypt
npx prisma init
```

1. Set `DATABASE_URL` in `.env.local` (use Neon free tier).
2. Add User / Account / Session / VerificationToken models from the Auth.js Prisma adapter docs.
3. Add the Task model:

```prisma
model Task {
  id          String   @id @default(cuid())
  title       String
  done        Boolean  @default(false)
  dueAt       DateTime?
  createdAt   DateTime @default(now())
  updatedAt   DateTime @updatedAt

  userId      String
  user        User     @relation(fields: [userId], references: [id], onDelete: Cascade)

  @@index([userId])
  @@index([userId, done])
}
```

4. `npx prisma migrate dev --name init`
5. Create `auth.ts` with GitHub provider only. Three-line `app/api/auth/[...nextauth]/route.ts`.
6. Sign-in page: one button, `signIn("github", { callbackUrl: "/dashboard" })`.
7. `app/dashboard/page.tsx` server component: `const session = await auth(); if (!session) redirect("/login"); return <h1>Signed in as {session.user.name}</h1>`.

At this point: you can sign in with GitHub and see your name. Commit. You've integrated 4 of the 6 Phase 3 concepts already.

#### Phase B — read + create tasks (Day 2)

1. `lib/queries/tasks.ts`:

```ts
export async function getTasks(userId: string, filter: "all" | "open" | "done") {
  return db.task.findMany({
    where: {
      userId,
      ...(filter === "open" ? { done: false } : filter === "done" ? { done: true } : {}),
    },
    orderBy: [{ done: "asc" }, { createdAt: "desc" }],
  });
}
```

2. `app/dashboard/actions.ts`:

```ts
"use server";
import { z } from "zod";
import { revalidatePath } from "next/cache";

const CreateSchema = z.object({
  title: z.string().min(1, "Title required").max(200),
  dueAt: z.string().optional(),
});

export async function createTask(prev: { error?: string }, formData: FormData) {
  const session = await auth();
  if (!session?.user) return { error: "Unauthorized" };

  const parsed = CreateSchema.safeParse({
    title: formData.get("title"),
    dueAt: formData.get("dueAt") || undefined,
  });
  if (!parsed.success) return { error: parsed.error.issues[0].message };

  await db.task.create({
    data: {
      title: parsed.data.title,
      dueAt: parsed.data.dueAt ? new Date(parsed.data.dueAt) : null,
      userId: session.user.id,
    },
  });
  revalidatePath("/dashboard");
  return {};
}
```

3. `TaskForm.tsx` ('use client') uses `useFormState(createTask, {})` and `useFormStatus()` for the submit button.

4. `app/dashboard/page.tsx`:

```tsx
const session = await auth();
if (!session?.user) redirect("/login");
const tasks = await getTasks(session.user.id, "all");

return (
  <main>
    <h1>Tasks</h1>
    <TaskForm />
    <TaskList tasks={tasks} />
  </main>
);
```

Commit. You've got create + read working end-to-end. Already a usable app.

#### Phase C — update + delete + filter (Day 3)

1. Add `toggleTask(id)` and `deleteTask(id)` server actions.
2. `TaskRow.tsx` ('use client'): checkbox calls `toggleTask`, x-button calls `deleteTask`.
3. `FilterTabs.tsx` ('use client'): updates `?filter=open|done|all` in the URL. The server component reads `searchParams` and passes it down to `getTasks`.

Two patterns to internalise here:

- **Server actions take primitive args** (a task ID), not big objects. Easy to call from anywhere.
- **`revalidatePath("/dashboard")` after each mutation** so the list re-renders with fresh data without you wiring a refresh.

#### Phase D — polish (Day 4)

- Loading spinner on the submit button via `useFormStatus`.
- Inline error message above the form when validation fails.
- Empty state ("No tasks yet — add one above").
- Tiny header with the user's avatar + sign-out button (client component using `useSession`).
- Optimistic UI on the checkbox toggle (optional — `useOptimistic` from React 19).
- Proper TypeScript on every action's return shape.

#### Phase E — deploy (Day 5)

1. Push to a GitHub repo.
2. Sign in to Vercel, "Add New Project," pick the repo.
3. Get a *production* Neon database (separate from dev). Copy the pooled URL.
4. Create a *production* GitHub OAuth app with the prod callback URL.
5. Paste all env vars into Vercel (Production scope).
6. Click Deploy. Wait ~90 seconds.
7. Sign in to your live URL. Add a task. Open the URL on your phone — same task is there because it's coming from real Postgres.

8. Optional: custom domain via Vercel's Domains tab. CNAME at your DNS provider. Wait 5 min.

Commit, push, celebrate.

### What a senior would review you on

The code in each file. Specifically:

1. **Every server action calls `auth()` first.** Authorization is the first line, before any DB read or write. No exceptions.

2. **Every task DB query filters by `userId`.** Even `getTask(id)` should be `findFirst({ where: { id, userId: session.user.id } })` — you never let one user pull another's tasks by guessing IDs.

3. **Zod on every input.** Inputs from the client are untrusted. Validate at the boundary.

4. **`select` on every Prisma query.** Don't return more than the page needs. A `select: { id, title, done, dueAt }` is smaller, faster, and immune to schema additions.

5. **No `useEffect`-driven data fetching.** Reads happen in server components. Mutations happen via server actions. The only client state is interactive UI state (filter selection, drag state).

6. **Errors are *handled*, not thrown silently.** Server actions return `{ error: "..." }` for validation; throw only for truly unexpected database failures. The error boundary catches the throws.

7. **No secrets in the bundle.** A reviewer searches the client bundle for `STRIPE_SECRET`, `DATABASE_URL`, `AUTH_SECRET` — finds nothing. Open Network → check the JS chunk for known prefixes.

8. **The migration history matches reality.** No schema changes outside of `prisma migrate dev`. Every column in production exists because a committed migration file added it.

### Common pitfalls (and the fix)

- **`session.user.id` is `undefined` in server actions.** Default Auth.js doesn't expose the ID on the session. Add the `jwt` + `session` callbacks (see `authjs` concept) to copy `user.id` into the JWT and out into `session.user`.

- **TypeScript complains about `session.user.id`.** Default `Session` type doesn't include `id`. Create `next-auth.d.ts`:

```ts
import "next-auth";
declare module "next-auth" {
  interface Session {
    user: { id: string; name: string; email: string; image: string };
  }
}
```

- **"My local data shows but prod is empty."** You ran `prisma db push` against your dev DB instead of `migrate dev`. Production was provisioned via `migrate deploy` which only reads migration files, so it never got the schema. Fix: run `prisma migrate dev` to generate the migration file, commit it, redeploy.

- **`P1001 Can't reach database`** in production. Your `DATABASE_URL` in Vercel is wrong, or your Neon DB is sleeping (free tier sleeps after 5 min idle on the free plan). Fix the URL or upgrade Neon to a "scale to zero" plan that wakes faster.

- **OAuth callback URL mismatch.** You added your prod URL to env vars but forgot to update the GitHub OAuth App's callback URL. Symptom: "redirect_uri_mismatch" error from GitHub. Add `https://your-app.vercel.app/api/auth/callback/github` to the OAuth App.

Each of these is a 60-second fix once you know the symptom. Don't be afraid of them — they're the texture of shipping.
